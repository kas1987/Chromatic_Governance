# Product Operating Model

## Purpose

Use product-family skills to keep agent work tied to user value, validated outcomes, and release discipline. Product artifacts should reduce ambiguity before architecture, implementation, QA, docs, and release work begins.

## Operating principles

1. Start with the user problem and outcome.
2. Separate evidence from interpretation.
3. Keep scope smaller than instinct suggests.
4. Convert decisions into testable requirements or acceptance criteria.
5. Make non-goals explicit.
6. Record assumptions and what would invalidate them.
7. Route work to the correct family once product intent is clear.

## Evidence levels

| Level | Meaning | Product handling |
|---|---|---|
| L0 | Pure idea or intuition | Treat as assumption; prefer prototype or discovery. |
| L1 | Single anecdote or stakeholder request | Capture but avoid broad conclusions. |
| L2 | Repeated qualitative signal | Theme and size the opportunity. |
| L3 | Quantified behavioral or support trend | Prioritize against impact and cost. |
| L4 | Validated experiment or direct revenue/user impact | Consider roadmap or release commitment. |

## Handoff routing

- Send unclear product direction to `requirements` or `user-story`.
- Send bloated work to `scope-cut`.
- Send feature sequencing to `prioritize` or `roadmap`.
- Send design friction to `ux-critique`.
- Send raw customer input to `feedback-loop`.
- Send ready work to architecture, QA/eval, security, docs, and release families.
