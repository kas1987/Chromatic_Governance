# MVP Plan

## Mission

Design the smallest credible release that proves or disproves the core product bet.

## Inputs to collect

- Target user and problem
- Product bet or hypothesis
- Desired outcome and success metric
- Current assets, constraints, and deadline
- Required integrations, data, permissions, and risks
- Evidence level: known demand, weak signal, or assumption

## Procedure

1. State the product hypothesis clearly.
2. Define the minimum user journey that tests the hypothesis.
3. Identify must-have capabilities for that journey only.
4. Separate MVP, v1, v1.1, and future bets.
5. Define success metrics and failure signals.
6. Identify build, QA, security, docs, and release gates.
7. Produce a phased plan with decision points.

## Guardrails

- MVP does not mean low quality. Keep safety, reliability, and clear feedback paths.
- Do not include features that do not test the main hypothesis.
- Do not inflate the MVP to satisfy every stakeholder.
- If evidence is weak, recommend a prototype or concierge test before full build.

## Expected output

- MVP hypothesis
- Target user and core journey
- Must-have scope
- Explicitly deferred scope
- Success metrics and stop/go criteria
- Build phases
- Risks and dependencies
- Recommended next handoff
